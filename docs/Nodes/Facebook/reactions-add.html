reactions/add

Add a reaction to a Facebook post. The Graph API does not permit apps to write reactions, so this operation cannot succeed — read this page before using it.

This operation cannot succeed against the live Graph API. POST /{post-id}/reactions is not a publishable endpoint. Meta removed programmatic reacting and liking when publish_actions was deprecated — reactions can be read by an app but not written, and no Facebook permission grants the ability. A correctly configured call will still fail at Facebook.

The operation is documented here because it appears in the palette and in the configuration schema. Do not build a workflow that depends on it. See Roadmap for its status.
Palette name: Add Reaction to Facebook Post  ·  Graph call: POST /{postId}/reactions  ·  Permissions: none available  ·  Field reference: Reactions

What Actually Happens

The node's local validation is fully implemented, so the two behaviours are quite different:

InputResult
An invalid reaction type, e.g. THUMBSFails locally with FACEBOOK_VALIDATION_ERROR. No request is sent.
A blank or short token, or a blank post IDFails locally with FACEBOOK_AUTH_ERROR or FACEBOOK_VALIDATION_ERROR.
A completely valid configurationReaches Facebook and fails there — typically FACEBOOK_API_ERROR carrying a Graph (#200) permissions error.

In other words: the node behaves correctly and the Graph API refuses the action. Reporting this as a node defect is a false lead — check the raw Graph response on the error port before investigating further.

What to Do Instead

  • To acknowledge a post publicly, use post/comment. A Page comment is visible, attributable, and fully supported.
  • To acknowledge privately, use message/send, subject to the PSID and 24-hour window rules.
  • To count reactions on a post, reading is permitted — but the node has no read operation for it. Use an HTTP Request node against GET /{postId}/reactions?summary=true with the same Page token.

Configuration

Documented for completeness. The fields are read and validated as described.

FieldRequiredDescription
resourceRequiredMust be reactions.
operationRequiredMust be add.
pageAccessTokenRequiredPage access token, or a stored credential. Minimum 100 characters.
postIdRequiredPost ID in {pageId}_{postId} form.
reactionTypeRequiredOne of LIKE, LOVE, HAHA, WOW, SAD, ANGRY, HUH. Case-insensitive — the value is uppercased before checking.

In the properties panel Reaction Type is a dropdown offering Like, Love, Haha, Wow, Sad, Angry, and Huh.

Output Contract

Were the endpoint to succeed, the success port would carry:

FieldTypeDescription
statusstring"success"
items[0].successbooleanAlways true on the success port.
items[0].postIdstringThe post ID, echoed from the input.

Expected Failure

{
  "status": "error",
  "errorCode": "FACEBOOK_API_ERROR",
  "errorMessage": "(#200) Permissions error"
}

The exact Graph message varies. The raw response body is carried through with the error — read it rather than the code alone, since Facebook frequently returns HTTP 200 with an error envelope, which the node maps to FACEBOOK_API_ERROR rather than a permission-specific code.

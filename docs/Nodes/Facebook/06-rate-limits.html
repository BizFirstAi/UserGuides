Rate Limits & Validation

Automatic retry behaviour, request timeouts, Facebook's own throttles, the node's local validation limits, and which operations are safe to retry.

Automatic Retry

Every Facebook request passes through a retry handler. You do not configure it and you cannot disable it.

BehaviourValue
Retries onHTTP 429 and every 5xx
Maximum retries3 — four attempts in total
Delay between attemptsThe Retry-After header, capped at 60 seconds. Defaults to 1 second when the header is absent.
Request bodiesCloned per attempt, so writes retry correctly
After the last retryFACEBOOK_RATE_LIMIT for 429, FACEBOOK_SERVICE_ERROR for 5xx
Two consequences worth designing around.
• A throttled call can occupy the node for roughly three minutes before surfacing an error. That is the retry schedule working, not a hang.
• Because request bodies are re-sent, a write that appeared to fail may have succeeded. A page/post that timed out can still have published. Check the Page before re-running any write.

Timeouts

OperationsTimeout
page/*, post/*, message/*, reactions/*, moderation/*30 seconds
media/uploadImage, media/uploadVideo120 seconds

The media timeout is longer because Facebook has to fetch the file from your URL before responding. It bounds the request, not the encode — video processing continues on Facebook's side after the node returns. See media/uploadVideo.

A timeout that is not a user cancellation surfaces as FACEBOOK_TIMEOUT.

Facebook's Own Limits

Meta applies app-level and per-endpoint throttles that this node does not track or surface beyond the error codes. Two you will meet:

Graph errorScope
(#4) Application request limit reachedApp-wide. Every workflow using the same app shares this budget.
(#613) Calls to this api have exceeded the rate limitPer endpoint.

Meta's exact quotas vary by app, Page size, and endpoint, and change without notice. Check the current Graph API rate-limiting documentation before designing a high-frequency workflow.

Designing Within the Limits

PracticeWhy
Poll at the slowest interval you can tolerateEvery scheduled run is a Graph call whether or not anything changed. Fifteen minutes is usually enough for Messenger; hourly or daily is plenty for feeds.
Raise limit instead of looping moreOne call returning 50 records costs less quota than two returning 25.
Deduplicate before writingRe-hiding comments you already hid burns quota and achieves nothing. See Examples.
Stop paginating when the cursor emptiesA loop that keeps calling with an exhausted cursor wastes calls.
Separate apps per environmentDevelopment polling should not consume the production app's budget.
Wire the error portOtherwise a sustained throttle looks like a workflow that quietly stopped working.

Local Validation Limits

These are enforced by the node itself. When one fires, no request reached Facebook — do not go looking on the Meta side.

The token-length rule is inconsistent, and that is worth knowing. The same short or truncated token is rejected locally by page/post but sails past page/getInfo and fails at Facebook with (#190). One bad token, two different-looking errors. Also note that post/update does not length-check its message, even though the properties panel advertises the 63,206 limit.

Input Normalisation

Before validation, every input is normalised:

  • Required fields are trimmed. Leading and trailing whitespace is removed silently, not rejected. This exists because a trailing space on a Page ID once produced a malformed URL.
  • Optional fields collapse to nothing when blank, and are then dropped from the request entirely rather than sent as empty values. This is what keeps an unused picture from triggering (#100) Only owners of the URL have the ability to specify the picture.

Practical effect: leaving an optional field blank is exactly the same as omitting it, and you never need to clean whitespace out of a Page ID yourself.

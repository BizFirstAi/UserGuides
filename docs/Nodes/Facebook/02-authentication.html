Authentication

Obtaining a Facebook Page access token, storing it safely, the Graph permission each operation needs, and when App Review becomes mandatory.

Most first-run failures are token problems, not workflow problems. Work through this page before wiring up any operation, and verify the token with debug_token before you conclude the node is at fault.

What the Node Needs

A Facebook Page access token — not a User token, not an App token — carrying the right permissions, plus the numeric Page ID for most operations.

The node consumes a token that already exists. It has no OAuth flow, and no operations for exchanging, refreshing, or revoking tokens. Issuance and rotation are manual and external, so plan for that in operations.

The token is sent as an Authorization: Bearer <token> header. The node never uses the ?access_token= query parameter — worth knowing when comparing node behaviour against a Graph API Explorer session, which does.

Storing the Token

The node resolves its token in a fixed order:

  1. Stored credential — when credentialID is set in the node config, the value comes from the Credentials Manager.
  2. Inline — otherwise, the pageAccessToken config key is used.

A stored credential always wins. If both are present the inline value is ignored entirely. Neither present produces this on the error port:

pageAccessToken is required. Set credentialID in the node config or
provide pageAccessToken inline.
Use a stored credential in anything but local development. An inline token lives in the workflow definition, visible to everyone with read access to the process and carried into every export and backup. Create the credential once in the Credentials Manager with type BEARER_TOKEN and value set to the Page access token, then select it on the node's Credentials tab.

Obtaining a Page Token

Quick path — good for a day of testing

  1. Open developers.facebook.com/tools/explorer.
  2. Select your app under Meta App, and User Token under User or Page.
  3. Tick the permissions from the table above, then Generate Access Token and complete the dialog, granting your test Page.
  4. Call GET /me/accounts. For each Page the response gives id — your Page ID — and access_token — your Page token.

This Page token inherits the User token's one-to-two-hour expiry. Fine for one pass; use the durable path for anything longer.

Durable path — a non-expiring Page token

# 1. Exchange the short-lived user token for a long-lived one (60 days)
curl -s "https://graph.facebook.com/v25.0/oauth/access_token\
?grant_type=fb_exchange_token\
&client_id=<APP_ID>\
&client_secret=<APP_SECRET>\
&fb_exchange_token=<SHORT_LIVED_USER_TOKEN>"
# -> { "access_token": "<LONG_LIVED_USER_TOKEN>", "expires_in": 5184000 }

# 2. Derive the Page token FROM the long-lived user token
curl -s "https://graph.facebook.com/v25.0/me/accounts\
?access_token=<LONG_LIVED_USER_TOKEN>"
# -> data[]: { "id": "<PAGE_ID>", "name": "...", "access_token": "<PAGE_TOKEN>" }
Step 2 must use the long-lived token. A Page token derived from a long-lived user token does not expire. Deriving it from the short-lived token gives you a short-lived Page token that dies in an hour — and this is the most common setup mistake by a wide margin.

A non-expiring Page token still dies if the user changes their password, revokes the app, or loses admin rights on the Page. Treat a sudden (#190) across every operation as a sign one of those happened.

Verifying the Token

curl -s "https://graph.facebook.com/v25.0/debug_token\
?input_token=<PAGE_TOKEN>\
&access_token=<APP_ID>|<APP_SECRET>"

Finding the Page ID

  • GET /v25.0/me/accounts with a user token — returns id per Page
  • Page → Settings → About
  • GET /v25.0/{page-username}?fields=id,name
  • GET /v25.0/me?fields=id while a Page token is selected

App Review

Not needed for internal development or testing. Keep the app in Development mode: every permission works at full fidelity, but only for users holding an app role and only on Pages those users administer. That is exactly the test setup described above, so App Review should never block a QA cycle.

App Review plus Business Verification become mandatory when the app goes Live — when real customers connect their own Pages. At that point every permission needs Advanced Access.

pages_manage_metadataStandard review. Needed for webhook subscription.

pages_messagingStrictest. Requires a screencast and a stated messaging use case. The longest lead time — start it first.
business_managementOnly when Pages are Business-Manager-owned.

Begin App Review in parallel with development rather than after it. pages_messaging is the long pole.

Token Hygiene

  • Never paste a token into a shared document, chat, or ticket. A Page token grants publish and delete rights on the Page.
  • Use the Credentials Manager, so the secret is not readable by everyone with access to the process definition.
  • Rotate on team changes. Revoke via Page Settings → Business Integrations → remove the app, then re-issue.
  • Separate tokens per environment. A development workflow pointed at a production Page publishes to a real audience.
  • Tokens must not appear in logs. The node does not log them; check that your own Function and Code Execute nodes do not either.

Troubleshooting

A two-minute isolation ladder, every node and Graph error code, and a symptom index covering the failures people actually hit.

Start Here: the Isolation Ladder

When a Facebook node fails, this sequence separates a node problem from a Facebook configuration problem in about two minutes. Work down it in order — each step rules out everything above it.

StepCheckIf it fails
1debug_token — is the token valid, type: PAGE, with the right scopes?The token is the problem. See Authentication.
2Raw curl to the same Graph endpointFacebook is rejecting the call itself. The node is not involved.
3The same curl from the workflow hostNetwork egress, DNS, TLS, or firewall.
4The node with an inline tokenThe node or its configuration.
5The node with a stored credentialCredential resolution — check credentialID and the stored value.
6The full workflow runExpressions or wiring — configuration is not reaching the node as expected.

The code alone can mislead. Graph frequently returns HTTP 200 with an error envelope in the body. Those become FACEBOOK_API_ERROR rather than the status-derived code — so a permission problem can legitimately arrive as FACEBOOK_API_ERROR and not FACEBOOK_PERMISSION_ERROR. Always read the raw response before drawing a conclusion.

Symptom Index

"It worked yesterday and now everything fails with (#190)"

The token died. A non-expiring Page token is revoked when the user changes their password, removes the app, or loses admin rights on the Page. It also happens when the token was derived from a short-lived user token by mistake — that Page token expires in about an hour. Re-issue via the durable path in Authentication.

"page/getInfo works but page/post fails with an auth error"

Expected, and it is a real inconsistency in the node. Eight operations enforce a 100-character minimum on the token; the other six only check that it is non-blank. A short or truncated token therefore passes the lighter check, reaches Facebook, and fails there — while the same token is rejected locally by the stricter operations. Both are symptoms of one bad token.

"The operation does not run at all — unsupported operation"

The resource and operation pair did not match. Operation names are camelCase and matched exactly: getFeed, not getfeed, GetFeed, or get-feed. The kebab-case form shown in the panel subtitle is a display label. Configuration copied from the Instagram or WhatsApp nodes will not route, because those genuinely use kebab-case.

"The node succeeded but I cannot iterate the results"

page/getFeed, post/getComments, message/getConversations, and page/getInsights return one item whose field holds the raw Graph JSON as a string. Parse it first. See Input & Output.

"message/send reports success but messageId is empty"

Normal. Facebook does not reliably return a message ID for that endpoint, and the node emits "" rather than omitting the field. Treat the success port — not a populated messageId — as confirmation.

"message/send fails with a policy error"

Either the recipient is not a PSID, or the 24-hour messaging window has closed. A PSID exists only after that person messages your Page, and a Page may reply freely only within 24 hours of their last message. Neither can be worked around with this node.

"reactions/add always fails"

Expected. The Graph API does not permit apps to write reactions and no permission grants it. This is not a node defect — see reactions/add.

"Media upload fails but the URL opens fine in my browser"

Facebook fetches the URL, not your machine. The host must be reachable from the public internet, serve the file without authentication, and present a valid certificate. Presigned URLs that expire quickly, VPN-only hosts, and localhost addresses all fail. The node's local check only validates the URL's shape, so this surfaces as a Graph error.

"A media upload times out"

Both media operations use a 120-second timeout because Facebook fetches and processes the source file while the request is open. A very large or slow-to-fetch video can still exceed it.

  • Host the source file on fast storage, geographically close to the workflow host if possible.
  • For large videos, check the file size and bitrate against Facebook's current recommended upload limits before retrying.
  • Remember the request timing out does not mean the upload failed — check the Page before re-running. See media/uploadVideo.

"A run seems to hang for minutes"

A rate-limited call retries up to three times with delays honouring Retry-After up to 60 seconds — so it can occupy the node for roughly three minutes before reporting FACEBOOK_RATE_LIMIT. That is not a hang. See Rate Limits.

"A post appeared twice"

Retries re-send the request body. A write that timed out may still have succeeded on Facebook's side before the retry fired. Check the Page before re-running any write operation.

"Insights returns (#100) valid insights metric required"

page_impressions and page_engaged_users are deprecated for newer Pages, and the properties panel still suggests the first of those. Clear the Metric field so the node applies its working defaults, or enter page_impressions_unique,page_post_engagements explicitly.

"The moderation workflow keeps hiding the same comments"

Hidden comments are still returned by post/getComments. Track the comment IDs you have already actioned and filter them out. See Examples.

"Nothing happens and there is no error"

The error port is probably unwired. The node routes every failure there rather than throwing, so an unconnected error port makes a failure look like silence. Connect it to a notification, a Catch Block, or a logging step.

Before Reporting a Defect

  1. Run the isolation ladder above and note the step where it first fails.
  2. Capture the raw Graph response from the error port, not just the error code.
  3. Confirm with debug_token that the token is type: PAGE, valid, and carries the required scopes.
  4. Reproduce with curl to establish whether Facebook or the node is refusing.
  5. Redact the token from anything you attach.

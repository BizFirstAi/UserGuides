Roadmap & Known Gaps

What the Facebook node does not do yet — no webhook trigger, unsupported reactions, string-typed list output — the work needed to close each gap, and the workaround for now.

What the Facebook node does not do today, why, and what to use in the meantime. Nothing on this page is a defect — these are known boundaries.

No Facebook Trigger

The node is registered as an action. There is no webhook trigger and no trigger operation, so a workflow cannot currently be started by Facebook activity.

Groundwork exists but is not connected: the codebase contains a working HMAC-SHA256 signature validator for X-Hub-Signature-256 and full Messenger webhook payload models. Neither is reachable from a workflow — nothing calls them.

For comparison, the Instagram node does have a webhook trigger. The WhatsApp node is in the same position as Facebook: payload models present, trigger not implemented.

What to do today. Drive Facebook workflows from a Scheduled Trigger and poll:
• New posts → page/getFeed
• New comments → post/getComments
• New Messenger activity → message/getConversations

Track what you have already handled so each run only acts on what is new, and pick the interval with Rate Limits in mind. For Messenger, poll often enough to answer inside the 24-hour window.

Live Messenger webhook receiving does exist elsewhere in the platform as a channel integration. That is a separate product surface, not part of this node, and it is not driven from a workflow canvas.

What is needed to finish it

Four pieces of work stand between the current state and a working Facebook trigger:

  1. A public webhook receiver endpoint — comparable to the process-webhooks/{processId}/{nodeId} pattern already used elsewhere in ProcessEngine — that accepts Facebook's subscription verification handshake (hub.challenge) and forwards signed POST payloads.
  2. Wiring that endpoint into the existing validator. The raw request body and the X-Hub-Signature-256 header need to reach FacebookWebhookValidator.ValidateSignature, using the Facebook App's App Secret.
  3. A trigger resource and operation on the executor, or a dedicated trigger node, that deserialises the webhook payload and starts or resumes a workflow run per event — mirroring how message and comment events already map onto the message and post resources for outbound calls.
  4. A config field for the App Secret, distinct from the Page access token. It is needed only for webhook signature verification, not by any operation documented in this guide.

The signature-verification and payload-parsing pieces are already built. The receiver endpoint and the trigger-routing wiring are the two blocking items.

reactions/add Cannot Succeed

The operation ships and validates its input correctly, but POST /{post-id}/reactions is not a publishable Graph endpoint. Meta removed programmatic reacting when publish_actions was deprecated. Reactions are readable by an app but not writable, and no permission grants the ability.

Its future is an open decision: remove the operation, or convert it into a getReactions read. Until then, treat it as unusable. Full detail on reactions/add.

Today: respond with post/comment, or read reaction counts with an HTTP Request node against GET /{postId}/reactions?summary=true.

List Operations Return Strings

Four operations return Facebook's response as a JSON string in a single item rather than as structured rows. Typed record shapes for feed items and conversation items exist in the codebase but nothing constructs them — an intended refactor that has not landed.

Until it does, place a Function, Code Execute, or JSON Transform node immediately after those operations. Patterns are on Input & Output and Examples.

Media Upload Is URL-Only

Neither media operation accepts binary content, a local file path, or a workflow attachment. Facebook's servers fetch the URL you supply, so the file must already be hosted somewhere publicly reachable.

Binary upload is an open question in the node's own design notes, so this may change. Today: stage the file first — an S3 node, for example — and pass the resulting public URL.

Open Questions from the Implementation Notes

The node's internal engineering notes record two points still under discussion:

QuestionDetail
Video and file upload handlingWhether to support direct binary or multipart upload from a workflow, rather than requiring a publicly reachable source URL. See Media Operations.
Webhook mechanicsThe end-to-end flow — subscription verification, endpoint shape, and how a received event maps onto a running or newly started workflow — is still being worked out beyond the signature-verification and payload-parsing pieces already built.

No Video Publish-Status Polling

Video publishing is asynchronous. A success port carrying a mediaId means Facebook accepted the video; encoding happens afterwards and can still fail. The node has no operation to check what happened next.

Today: follow the upload with a Delay and an HTTP Request node:

GET https://graph.facebook.com/v25.0/{mediaId}?fields=status
Authorization: Bearer <page access token>

Loop until status.video_status settles on ready or error.

No Token Lifecycle Operations

Unlike the Instagram node, which exposes token exchange, refresh, and revoke as operations, the Facebook node has none. Tokens are issued, rotated, and revoked entirely outside the workflow.

Plan for that operationally: a non-expiring Page token still dies when the owner changes their password, revokes the app, or loses Page admin rights, and the failure arrives as (#190) across every operation at once. A scheduled page/getInfo health check gives you early warning. The full manual procedure is on Authentication.

Reporting Something Not Listed Here

Before filing a defect, check Troubleshooting — particularly the isolation ladder, which separates a node problem from a Facebook configuration problem in a couple of minutes. Capture the raw Graph response from the error port, not just the error code, and redact the token before attaching anything.

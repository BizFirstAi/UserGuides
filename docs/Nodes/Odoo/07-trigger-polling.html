Trigger / Polling

Fire a workflow when Odoo records change, without a webhook — exactly-once, with a watermark cursor

resource: trigger — polls a chosen target (lead, contact, activity, or custom) for records whose write_date has advanced since the last cycle.

Configuration

Config KeyPurpose
targetResourceWhich resource to watch: lead, contact, activity, or custom
customModelOdoo model name, only used when targetResource is custom
domainOptional filter, AND-ed with the mandatory watermark clause
fieldsListFields to include on each emitted record
pollIntervalSecondsHow often the trigger checks for changes
pageSizeMax records drained per poll cycle — default 500

Why write_date

Every standard Odoo model carries a write_date timestamp via the base _log_access mixin, set on both create and update — there's no separate "created" stream to watch. One filter catches both new and modified records. The tradeoff: the trigger knows a record changed, never what field changed. A workflow that needs field-level deltas has to keep its own previous-value state and diff on receipt.

Activating on an Existing Instance

The first poll cycle seeds the cursor at "now" and emits nothing. Without this, turning on a trigger against a mature CRM with years of history would replay every historical record as if it had just changed — potentially tens of thousands of events at once. Changes made before the trigger was activated are not delivered; if you need those, run a Get Many over the historical range separately.

Exactly-Once Delivery — the Bulk-Import Problem

PostgreSQL's now() returns transaction-start time, so every record written in one transaction shares the exact same write_date — a 50,000-row bulk import produces 50,000 identical timestamps, not a microsecond spread. Since the poll query is inclusive (>=, so no boundary record is ever missed), a bare watermark alone would re-emit every record at that instant on every subsequent cycle, forever.

The trigger closes this gap by also tracking which record IDs were already emitted at the current watermark instant, clearing that set only once the watermark strictly advances past it. This is why the persisted cursor is more than just a timestamp.

Failure Holds the Cursor

If a poll cycle fails (network error, Odoo-side fault), the cursor is not advanced — the next cycle re-queries the exact same window. Worst case, records are re-fetched and re-deduplicated; nothing is skipped because of a transient outage.

Bounded Pages, Not Unbounded Drains

pageSize (default 500) caps how many records one poll cycle processes. This isn't only about payload size: an unbounded read of a large change batch would hit the platform's result-set ceiling and fail outright — and because a failed poll holds the cursor, every following cycle would re-query the same oversized window and fail identically, wedging the trigger permanently. A bounded page drains a large batch across several cycles instead of failing on the first one.

Production requirement: persistent cursor storage. The trigger's cursor is stored via the platform's distributed cache abstraction. Under the default in-memory cache provider, that state is lost on every process restart — after which the trigger finds no state, treats the next cycle as a first run, reseeds at "now," and silently skips every change made before the restart. Any deployment relying on this trigger for completeness must configure a persistent provider (Redis, SQL Server) for the distributed cache. See Roadmap.

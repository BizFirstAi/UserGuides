Examples

Four worked workflow patterns built from the operations covered in this guide.

1. Check an Account's HBAR Balance Before a Payout Step

Before a workflow triggers an off-ledger payout (e.g. releasing funds, marking an invoice paid, or unlocking a service), confirm that the treasury account actually holds enough HBAR to cover it.

{
  "resource": "account",
  "operation": "getBalance",
  "network": "mainnet",
  "accountId": "0.0.900321"
}
Workflow pattern: Feed tinybars from the response into an If Condition node comparing it against the required payout amount (converted to tinybars via utility.convertUnits). Route to the payout step only when the balance is sufficient; otherwise route to an alert/notification path so an operator can top up the treasury account before customers are affected.

2. Poll an HCS Topic for New Messages as a Trigger Pattern

Because this node's topic.getMessages operation is a synchronous read rather than a push-based subscription, the standard way to react to new HCS activity is to poll on a schedule and track the last sequence number seen.

// Scheduled Trigger fires this every 30 seconds
{
  "resource": "topic",
  "operation": "getMessages",
  "network": "mainnet",
  "topicId": "0.0.987654",
  "sequenceFrom": "{{ $vars.lastSequenceSeen + 1 }}",
  "limit": 50
}
Workflow pattern: Pair a Scheduled Trigger node with a Variable Assignment node that persists lastSequenceSeen between runs. On each run, if messages is non-empty, loop over it with a Loop node to process each event (e.g. parsing a JSON payload out of message) and update lastSequenceSeen to the highest sequenceNumber returned before the workflow ends. This turns an HCS topic into a lightweight, ordered event queue for any downstream automation.

3. Look Up Token Metadata and an Account's Token Balances Together

Raw token balances are just IDs and integers — pairing token.getBalances with token.getInfo resolves each holding into a human-readable name, symbol, and correctly-scaled amount.

// Step 1 — list what the account holds
{
  "resource": "token",
  "operation": "getBalances",
  "network": "testnet",
  "accountId": "0.0.1234567",
  "limit": 25
}

// Step 2 — for each tokenId in the result, resolve its metadata
{
  "resource": "token",
  "operation": "getInfo",
  "network": "testnet",
  "tokenId": "{{ $item.tokenId }}"
}
Workflow pattern: Feed the balances array from step 1 into a Loop node. Inside the loop, call token.getInfo for the current item's tokenId, then use a Data Mapping node to combine balance / decimals from step 1 with name / symbol from step 2 into a single display-ready row — e.g. "1,000.00 WDG (Widget Token)".

4. Convert a User-Entered HBAR Amount to Tinybar Before a Downstream Step

When a workflow accepts a human-entered amount (from a Form node, a chat message, or an approval step) in HBAR, convert it to tinybars before comparing it against any balance or fee value returned by other operations — those are always expressed in tinybars.

{
  "resource": "utility",
  "operation": "convertUnits",
  "amount": "{{ $form.requestedAmount }}",
  "fromUnit": "hbar",
  "toUnit": "tinybar"
}
Workflow pattern: Place this node right after the Form or Chat node that collects the user's HBAR amount, and before the If Condition node that compares it against a balance from account.getBalance. Comparing like-for-like units (tinybar to tinybar) avoids an entire class of off-by-100,000,000 bugs.
All four patterns above are read-only. None of them move value or submit anything to the ledger — they only inform decisions inside the workflow. See Roadmap for planned signed-write operations that would actually execute a transfer, mint, or topic submission.

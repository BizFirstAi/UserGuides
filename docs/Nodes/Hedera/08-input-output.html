Input & Output

The config-key pattern shared by every operation, the general output shape, and how errors surface.

The Common Config Pattern

Every Hedera node configuration — regardless of resource or operation — is built from the same three-part shape:

Config keyPresent onPurpose
resourceEvery operationSelects which family of functionality to invoke: account, token, topic, transaction, or utility.
operationEvery operationSelects the specific action within that resource, e.g. getBalance vs. getInfo under account.
networkEvery operation except the two utility operationsWhich Hedera network's Mirror Node to call. Optional — falls back to Hedera:DefaultNetwork. See Networks.
operation-specific fieldsVariese.g. accountId, tokenId, topicId, transactionId, amount — see each operation's own page for the exact field list.

This means learning any one operation on this node teaches you the shape of all of them — only the operation-specific fields change.

General Output Shape

Every successful call returns a flat JSON object scoped to that operation's own concerns — there is no deeply-nested "Hedera SDK response" wrapper to unwrap. Most responses also echo back the network that was queried, so downstream nodes and logs can tell at a glance which ledger the data came from. Collection-returning operations (token.getBalances, topic.getMessages) nest their rows under a single named array (balances, messages) rather than returning a bare array, so additional top-level metadata can be added later without a breaking change.

How Errors Surface

Because every read operation is ultimately an HTTP call to the Mirror Node REST API, errors generally trace back to one of two HTTP outcomes:

Mirror Node statusTypical causeWhat you see
404The requested account, token, topic, or transaction ID doesn't exist on the queried network — including a real ID queried against the wrong network (e.g. a mainnet account ID looked up on testnet).A not-found style error surfaces on the node's error output, with the resource type and ID included in the message so it's clear what wasn't found.
400The ID or parameter was malformed before it even reached the ledger — e.g. an account ID missing a segment, or a limit outside the 1–100 range.A validation-style error surfaces, generally before any HTTP call is even made for field-shape problems the executor can catch locally (like an out-of-range limit).

See Troubleshooting for the specific exception types raised for configuration problems (like an unconfigured network) versus ledger-level lookup failures, plus guidance on rate limiting and retries.

Fail fast on config problems. Structural problems the node can detect without a network call — an unknown resource/operation combination, a missing required field, or an unconfigured network — are rejected immediately, before any HTTP request goes out. Only once the request shape is valid does the node call the Mirror Node and interpret its HTTP response.

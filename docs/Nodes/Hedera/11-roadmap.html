Roadmap

Coming soon: signed write operations for the Hedera node.

Everything on this page is planned, not yet shipped. Every operation described elsewhere in this guide is a free, read-only Mirror Node query available today. The operations below require signing a transaction with a real Hedera private key and submitting it to the network — a fundamentally different, higher-trust capability that is still in design.

Planned Operations

The next phase of this node adds signed write operations, following the same resource/operation shape used by the reads in this guide:

ResourcePlanned operations
accountcreate — create a new Hedera account. transfer — send HBAR from a controlled account to another account.
tokenmint — mint additional supply of an HTS token. associate — associate an account with a token so it can hold a balance. transfer — move HTS tokens between accounts.
topiccreate — create a new HCS topic. submit — submit a message to an existing topic (the write-side counterpart of today's topic.getMessages).
(cross-cutting)Message signing — a lower-level primitive for signing arbitrary payloads with an account's key, for use cases beyond the transaction types above.

Same Pattern as the Reads

These will follow the same partial-class / service-per-resource pattern already used for the read operations documented in this guide — resource + operation selects the action, an operation-specific set of fields supplies the parameters, and a per-resource service in BizFirst.Integration.Hedera.Services implements the call. The difference is that instead of issuing a GET against the Mirror Node, these operations will construct, sign, and submit an actual transaction to the Hedera network.

Why the Hashgraph SDK

Submitting a signed transaction requires more than an HTTP client — it requires constructing the transaction bytes, computing signatures, and speaking Hedera's gRPC-based consensus node protocol, which is exactly what a native SDK provides. The intended dependency is the community Hashgraph .NET package (published by bugbytesinc), which is compatible with .NET 9 — matching every other project in this node.

Why not the official successor SDK? Hedera's newer official SDK, Hiero, currently targets .NET 10 only. Since this node's three projects (BizFirst.Integration.Hedera.Domain, .Services, and the executor) all target .NET 9 today, Hashgraph is the pragmatic choice until either this node's projects move to .NET 10 or Hiero adds .NET 9 support.

How Signing Credentials Will Be Resolved

Signed operations need a private key to sign with — and that key will never live in plain node configuration. The planned approach mirrors the pattern already used by the Ethereum node:

  • The signing credential is stored as a CRYPTO_WALLET record in the platform's credential vault, not inline in workflow configuration.
  • The executor's .Credentials.cs partial resolves it at execution time via ReadCredentialRawPrimaryAsync, deserializing the vault entry into a CryptoWalletRecord — the same call shape the Ethereum node already uses for its own signing credential.
  • Alongside the vault-resolved key, the write operation's config will supply a payer account ID (which account's balance funds the transaction fee) and a key algorithm field (e.g. ED25519 or ECDSA_SECP256K1) so the executor knows how to interpret the stored key material when constructing the signature.
Design goal: A private key should never need to pass through workflow-level configuration, logs, or the ProcessEngine's stored process definition in cleartext. The vault + CRYPTO_WALLET pattern keeps the signing secret entirely inside the credentials subsystem, with the executor only ever handling it in memory at the moment a transaction is signed.

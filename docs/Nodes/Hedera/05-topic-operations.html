Topic Operations

resource: topic — getMessages for the Hedera Consensus Service (HCS).

What is HCS? The Hedera Consensus Service lets any application submit arbitrary messages to a topic and get back a fair, timestamped, tamper-proof ordering from Hedera's consensus — without running its own ordering infrastructure. Many teams use HCS topics as an audit log, an event stream, or a trigger source for downstream automation.

topic.getMessages

Returns messages submitted to an HCS topic, in consensus sequence order.

FieldRequiredDescription
topicIdRequiredHCS topic ID in native form, e.g. 0.0.987654.
limitOptionalMaximum number of messages to return. Range 1–100, default 25.
sequenceFromOptionalOnly return messages with a sequence number greater than or equal to this value. Used to page forward through a topic without re-reading messages already processed.
decodeUtf8OptionalDefault true. When true, message contents (stored on-ledger as base64) are decoded to a UTF-8 string for you. Set false to receive the raw base64 payload instead — useful for binary or non-text message content.

Example Request

{
  "resource": "topic",
  "operation": "getMessages",
  "network": "testnet",
  "topicId": "0.0.987654",
  "limit": 25,
  "sequenceFrom": 101,
  "decodeUtf8": true
}

Example Response

{
  "topicId": "0.0.987654",
  "messages": [
    {
      "sequenceNumber": 101,
      "consensusTimestamp": "1690000012.345678900",
      "message": "{\"event\":\"order.shipped\",\"orderId\":\"ORD-2026-1042\"}",
      "payerAccountId": "0.0.1234567",
      "runningHash": "9f2a3c...e01b"
    },
    {
      "sequenceNumber": 102,
      "consensusTimestamp": "1690000048.912233100",
      "message": "{\"event\":\"order.delivered\",\"orderId\":\"ORD-2026-1042\"}",
      "payerAccountId": "0.0.1234567",
      "runningHash": "1b77de...4f90"
    }
  ],
  "network": "testnet"
}

Field Reference

FieldMeaning
sequenceNumberMonotonically increasing position of the message within the topic, assigned by consensus. Use the highest value seen as the next call's sequenceFrom to page forward.
consensusTimestampThe exact moment the network reached consensus on this message, as seconds.nanoseconds since the Unix epoch.
messageThe message payload — decoded UTF-8 text when decodeUtf8 is true (the default), or raw base64 when false.
payerAccountIdThe Hedera account that paid the fee to submit this message to the topic.
runningHashCumulative hash chaining this message to every prior message on the topic — lets a consumer verify the sequence hasn't been tampered with or reordered.

Sequence Ordering & Pagination

Messages are always returned in ascending sequenceNumber order — the same order consensus assigned them. To poll a topic incrementally (rather than re-fetching from the beginning every time), track the highest sequenceNumber your workflow has already processed and pass sequenceNumber + 1 as sequenceFrom on the next call:

// call 1 — no sequenceFrom, returns sequence numbers 1-25
{ "resource": "topic", "operation": "getMessages", "topicId": "0.0.987654", "limit": 25 }

// call 2 — resume after the last message processed (sequence 25)
{ "resource": "topic", "operation": "getMessages", "topicId": "0.0.987654", "limit": 25, "sequenceFrom": 26 }

See Examples for a full polling-as-trigger workflow pattern built on this technique.

Eventual consistency applies here too. A message submitted to a topic a moment ago may not yet appear via getMessages — the Mirror Node needs a few seconds to ingest new consensus events. Don't build a workflow that assumes a just-submitted message is immediately queryable; add a short delay or a retry loop instead. See Troubleshooting.

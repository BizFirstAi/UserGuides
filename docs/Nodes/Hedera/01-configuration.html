Configuration

appsettings.json, the network config key, host registration, and how the node's projects are laid out.

appsettings.json

The Hedera node reads its network endpoints from a Hedera section in application settings. Nothing else is required for read operations — there is no API key or credential to configure.

"Hedera": {
  "DefaultNetwork": "testnet",
  "Networks": {
    "mainnet":    { "MirrorRestUrl": "https://mainnet-public.mirrornode.hedera.com" },
    "testnet":    { "MirrorRestUrl": "https://testnet.mirrornode.hedera.com" },
    "previewnet": { "MirrorRestUrl": "https://previewnet.mirrornode.hedera.com" }
  }
}
SettingDescription
Hedera:DefaultNetworkName of the network used when a node configuration omits the network field. Must match a key under Hedera:Networks. Typically testnet for development.
Hedera:Networks:{name}:MirrorRestUrlBase URL of that network's Mirror Node REST API. The node appends the resource-specific path (e.g. /api/v1/accounts/{id}) when it calls out.
No credential required. Every operation currently shipped by this node is a read against the public Mirror Node REST API. There is nothing to store in the credentials manager and no signing key to configure — that changes only once the signed-write operations described in Roadmap ship.

The network Config Key

Every operation on this node accepts an optional network config key alongside resource and operation:

FieldRequiredBehavior
networkNoOne of the keys configured under Hedera:Networks (out of the box: mainnet, testnet, previewnet). When omitted, the node resolves Hedera:DefaultNetwork and uses that network's MirrorRestUrl. If the resolved network name has no matching entry under Hedera:Networks, the call fails before any HTTP request is made — see Troubleshooting for the exact exception.

Because network is just another config key, it can be set per-node, per-environment, or driven from a workflow variable/expression — for example, pointing a staging workflow at testnet while the equivalent production workflow points at mainnet, without changing any other field.

Registration

HederaDependency.RegisterDefaults(services) wires up everything the node needs in a single call:

  • The Mirror Node REST client (HederaMirrorClient, a typed HttpClient).
  • Per-resource services for account, token, topic, transaction, and utility operations.
  • The executor itself, registered with scoped lifetime.
  • An ExecutorRegistry entry for the hedera node type name, so INodeExecutorFactory can resolve it at runtime.
Host apps must also call registration explicitly. Add new HederaDependency().RegisterDefaults(services); to the host's node-plugin bootstrap — the Plugins_RegisterAllNodes(...) method in ServiceCollectionExtensionsForAI.cs — so the Hedera assembly is force-loaded and its executor is discoverable at runtime. Without this call the assembly may never load, and the hedera node type will not appear in the executor registry even though the NuGet/project reference is present.

Project Layout

The node ships as three .NET 9 projects, split by dependency weight:

ProjectResponsibility
BizFirst.Integration.Hedera.DomainSealed result records and network options. Zero external dependencies.
BizFirst.Integration.Hedera.ServicesThe Mirror Node REST client (HederaMirrorClient, a typed HttpClient) plus one service per resource (account, token, topic, transaction, utility).
BizFirst.Ai.ExecutionNodes.Blockchain.HederaThe executor — request routing by resource/operation, config validation, and the operation-specific DTOs.

This mirrors the layering used by other integration nodes: a dependency-free domain layer, a services layer that talks to the outside world, and an executor layer that adapts the services to the ProcessEngine node contract.

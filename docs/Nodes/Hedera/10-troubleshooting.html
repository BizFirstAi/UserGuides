Troubleshooting

Common errors, what causes them, and how to fix them.

Unconfigured Network

HederaNetworkNotConfiguredException

Cause: The network config key (or the resolved Hedera:DefaultNetwork value, when network is omitted) doesn't match any key under Hedera:Networks in application settings. This happens most often from a typo (testnett), a network referenced before it's added to configuration, or case mismatches.

Fix: Confirm the exact spelling of the network name against the keys in Hedera:Networks — see Networks. If you're pointing at a custom network entry, verify it was actually added to configuration in the environment the workflow is running in (a network added only in local appsettings.Development.json won't exist in production).

Invalid Address / ID Format

Malformed account, token, topic, or transaction ID

Cause: A field like accountId, tokenId, or topicId was not supplied in the expected native shard.realm.num form (e.g. 0.0.1234567), or a transactionId didn't match either of the two accepted formats — see Transaction Operations.

Fix: Run the value through utility.validateAddress before using it in any other operation, especially when the value comes from user input, a form, or an external system rather than a hard-coded configuration. For transaction IDs, accept either the native @ form or the dash form, but don't mix separators within a single ID.

Mirror Node Rate Limiting (HTTP 429)

Too Many Requests

Cause: The public Mirror Nodes are shared, free infrastructure and apply rate limits per client IP. A workflow that polls frequently (e.g. a tight HCS polling loop) or that fans out many parallel lookups can trip these limits, especially against testnet where limits tend to be lower than mainnet.

Fix:

  • Increase the interval between polling calls — for HCS message polling, 15–30 seconds is a reasonable starting point rather than sub-second polling.
  • Batch lookups where possible — request a larger limit in one call instead of many small calls in a loop.
  • Apply exponential backoff on retry: on a 429, wait, then retry with an increasing delay (e.g. 1s, 2s, 4s, 8s) rather than retrying immediately in a tight loop.
  • For sustained high-volume production usage, consider pointing Hedera:Networks at a self-hosted or commercially-hosted Mirror Node instead of the public community endpoints — see Networks for how to add a custom network entry.

Eventual Consistency — "It's Not There Yet"

A transaction, message, or balance change doesn't show up immediately

Cause: The Mirror Node ingests consensus events asynchronously and typically lags live Hedera consensus by a few seconds. This is expected, normal behavior of the Mirror Node REST API — not a bug in the node or a sign the transaction failed.

Fix: Don't chain a submission (via another tool/SDK) directly into a transaction.get, account.getBalance, or topic.getMessages call and expect the result to reflect it instantly. Instead:

  • Add a short delay (a few seconds) between submitting a transaction and querying for its result.
  • If you need to react to it, poll with a short retry loop (e.g. up to 5 attempts, a couple of seconds apart) rather than a single immediate lookup.
  • For HCS-based triggers specifically, favor the incremental sequenceFrom polling pattern in Examples over expecting a single message to appear the instant it's submitted.
Still stuck? Double-check the operation's exact field requirements on its own page — Account, Token, Topic, Transaction, Utility — and confirm the ID you're querying actually exists on the network you configured, not just on a different one.

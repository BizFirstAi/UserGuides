Connecting to Odoo & CRM

Why RealEstate is an addon to a CRM, not a CRM itself

RealEstate is an industry vertical. Odoo is an agent. RealEstate owns the property/listing domain — addresses, pricing, RESO/MLS fields, media, features — entirely itself, "not any CRM, so it stays portable across CRM providers" (straight from the source comments on the Property entity). Contact and lead management stay with a CRM — Odoo by default, reachable through the Odoo community node. The two are designed to sit side by side, connected by one explicit link, not merged into one system.

The mechanism: ExternalProvider + ExternalRecordID

Every Property carries two nullable fields:

FieldTypePurpose
ExternalProviderIDint?, FK → ExternalProviderWhich external CRM/system this property is linked to
ExternalRecordIDnvarchar(255)?That property's record id in the external CRM. A string, not an int, because not every provider uses integer ids

Both are NULL until a property is synced/linked — a draft listing created locally, before any CRM sync, is perfectly valid with no external link at all.

ExternalProvider is a real, seeded lookup table

RealEstate_ExternalProviders ships pre-seeded with:

ExternalProviderIDNameDescription
1OdooSelf-hosted Odoo Community CRM

The schema's own design comments explicitly name Odoo, Twenty, and EspoCRM as the kind of systems this table is meant to hold — Odoo ships first because the Odoo community node already exists (Contacts/Leads/Activities/CRM pipeline actions). Adding support for another CRM is a new ExternalProvider row plus whatever sync logic targets it — RealEstate's own schema and API don't change.

What actually gets linked — and what doesn't

  • Properties link to external records. A property's listing data can point at a matching record in Odoo (or another CRM) via ExternalProviderID/ExternalRecordID.
  • Agents do not. Agent is a local directory, deliberately not a CRM contact record — it is not linked via ExternalProvider. If you need a real-estate agent as a CRM contact too, that's a separate Odoo res.partner record, related by convention (e.g. matching email) rather than a foreign key RealEstate maintains.
  • The link is per-property, not per-tenant. Different properties in the same tenant can link to different providers, or to none at all.

Working with the link

OperationRoute
Link a property to an external recordPATCH api/v1/realestate/properties/external-link
Clear a property's linkPOST api/v1/realestate/properties/external-unlink
Find the property for a known external recordPOST api/v1/realestate/properties/by-external-record — returns a LIST, the pair is indexed but not unique
Every property linked to a given providerPOST api/v1/realestate/properties/by-external-provider
The sync backlog — properties not yet linked to anythingPOST api/v1/realestate/properties/unlinked

Design intent

This shape is deliberate: RealEstate never queries Odoo directly, and Odoo's node never knows about RealEstate_* tables. Whatever process syncs a property to a CRM record (an import job, a workflow built on the Odoo node, a manual link) is the only thing that needs to know about both sides — RealEstate itself just stores the pointer. That keeps RealEstate reusable for a future vertical's analogous entity, and keeps it working the same way whether the CRM behind ExternalProviderID is Odoo, Twenty, EspoCRM, or something else entirely.

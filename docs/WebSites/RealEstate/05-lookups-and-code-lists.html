Lookups & Code Lists

Six lookup resources, all following the same shape — plus two hard-coded code lists

The lookup resources

Each is a simple named/ordered catalog: {Name}, optional Description, DisplayOrder (default 0). All have a UNIQUE-per-name constraint that is not scoped by TenantID except PropertyCategory (scoped by its parent PropertyTypeID).

ResourceTableBase routeValues
PropertyTypeRealEstate_PropertyTypesapi/v1/realestate/property-typesResidential, Commercial, Land, Industrial, Mixed-Use
PropertyCategoryRealEstate_PropertyCategoriesapi/v1/realestate/property-categoriesNested under a PropertyTypeID, e.g. Single Family under Residential
ListingTypeRealEstate_ListingTypesapi/v1/realestate/listing-typesFor Sale / For Rent / For Lease
ListingStatusRealEstate_ListingStatusesapi/v1/realestate/listing-statusesDraft, Active, Pending, Under Contract, Sold, Leased, Off Market, Withdrawn, Expired
MediaTypeRealEstate_MediaTypesapi/v1/realestate/media-typesPhoto, Floor Plan, Virtual Tour, Document, Video
FeatureTypeRealEstate_FeatureTypesapi/v1/realestate/feature-typesGarage, Pool, etc. — each carries a ValueDataType (see below)

PropertyType and PropertyCategory additionally carry ShortDescription, IconUrl, and ImageUrl for richer UI surfaces.

The PropertyType / PropertyCategory pairing gap

The database does NOT enforce that a Property's chosen category actually belongs to its chosen type. Property.PropertyTypeID and Property.PropertyCategoryID are independent foreign keys. Because a category row knows its own PropertyTypeID, it is the source of truth for validating that pairing — and that validation happens in the service layer (PropertyController.CreateListing / .Reclassify reject a mismatched pair), not the database.

ExternalProvider

Also a lookup (RealEstate_ExternalProviders, base route api/v1/realestate/external-providers) but conceptually distinct from the six above — it's not a Property classification, it's the CRM/system a Property can link out to. See Connecting to Odoo & CRM.

Hard-coded code lists (not database tables)

Two small, closed value sets enforced by SQL CHECK constraints and mirrored as C# static classes for compile-time safety:

Code listGovernsValuesConstraint
AssociationFeeFrequenciesProperty.AssociationFeeFrequencyMonthly, Quarterly, Annually, OneTimeCK_RealEstate_Properties_AssociationFeeFrequency. Column is nullable — the CHECK evaluates to UNKNOWN (passes) for NULL, so "no value" is legal, but any non-null value outside the list is rejected.
FeatureValueDataTypesFeatureType.ValueDataTypeBoolean, Text, NumberCK_RealEstate_FeatureTypes_ValueDataType. NOT NULL, DB default 'Boolean' — unlike AssociationFeeFrequencies, there is no legal "no value" state here.

FeatureValueDataTypes.IsValueCompatible(dataType, featureValue) validates a PropertyFeature.FeatureValue against its declared type: Boolean accepts only "0"/"1", Number requires a parseable decimal, Text accepts anything. A null/empty value is always allowed regardless of type — "feature absent" is a legitimate state.

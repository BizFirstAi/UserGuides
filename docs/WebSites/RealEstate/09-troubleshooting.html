Troubleshooting

Gotchas that come from the schema's design, not bugs

"By MLS number" / "by parcel number" / "by external record" all return lists, not a single record. None of MLSNumber, ParcelNumber, or the (ExternalProviderID, ExternalRecordID) pair carry a uniqueness constraint. Code that assumes exactly one result and grabs the first element will silently pick an arbitrary row when duplicates exist from repeated imports.
Agent.MlsId is not unique either. /agents/by-mls-id can legitimately return more than one agent. /agents/match reports whether its match was ambiguous instead of silently guessing — check that flag rather than assuming the first result is correct.
Soft-deleting a Property does not remove its media or features. The database cascade only fires on a hard delete. If you soft-delete via DELETE /{id} instead of POST /delete-with-children, the property's PropertyMedia and PropertyFeature rows are left live and orphaned-looking — use delete-with-children unless you specifically want that.
PropertyCategoryID is not validated against PropertyTypeID by the database. Both are independent FKs. If you write directly to the database (bypassing CreateListing /Reclassify), nothing stops you from pairing a category that belongs to a different type — the mismatch is only caught by the service layer's own validation, not a SQL constraint.
Status changes don't auto-stamp lifecycle dates. RealEstate_ListingStatuses has no stable Code column, only an auto-increment id and a display name — so moving a listing to whatever id represents "Sold" does not automatically set CloseDate. You must pass it explicitly on PATCH /listing-status. If you need status-driven stamping, that requires a schema change (a Code column or agreed well-known ids) — see Roadmap.
PrivateRemarks will leak if you build a public projection carelessly. There is no field-level authorization on the Property entity itself — any code building a consumer-facing view from the raw entity must explicitly strip PrivateRemarks. It exists specifically to separate agent-only notes from public marketing copy (PublicRemarks); nothing enforces that separation automatically at the API layer.
IsPrimary is not DB-constrained to one row per property. Legacy or imported data can hold more than one "primary" photo. /property-media/primary returns a list for exactly this reason — don't assume a single result.
Setting a feature via the wrong endpoint fails the unique constraint. Use POST /property-features/set or /set-many (upserts) for anything import-driven — the generic Create endpoint will violate UQ_RealEstate_PropertyFeatures_PropertyID_FeatureTypeID on a second write for the same property+feature pair.
